# Deployment

The demo runs on free tiers:

| Part | Host | Notes |
|---|---|---|
| Front end | GitHub Pages | Static build of `frontend/`, published by `.github/workflows/pages.yml` |
| API | Render (free web service, Docker) | Defined in `render.yaml`; sleeps after 15 minutes idle, about a minute to wake |
| Database | Neon (free PostgreSQL) | 1 GB; compute suspends after 5 minutes idle |

```
Browser -> GitHub Pages (React) -> Render (FastAPI) -> Neon (PostgreSQL)
```

Limits above were read from each provider's pricing pages on 2026-10-05 and change often.
Check them again before relying on them.

## Configuration

| Variable | Where | Purpose |
|---|---|---|
| `DATABASE_URL` | Render (dashboard) | Neon connection string. Use the **direct** one (no `-pooler` in the host). A plain `postgresql://` URL is accepted. |
| `SECRET_KEY` | Render (generated by `render.yaml`) | Signs login tokens. |
| `ENVIRONMENT` | Render (`production`) | The API refuses to start in production with the development secret. |
| `CORS_ORIGINS` | `render.yaml` | Origin the browser app is served from (`https://coutlike.github.io`, no path). |
| `VITE_API_URL`, `VITE_BASE` | `pages.yml` | API address and base path, baked into the front-end build. |

Secrets live in the provider dashboards, never in git.

## First deploy

1. **Neon:** create a project and copy the direct connection string.
2. **Render:** New, then Blueprint, pick this repository. Enter `DATABASE_URL` when asked. The API
   creates the tables itself on first start (`alembic upgrade head`).
3. **GitHub Pages:** repository Settings, Pages, Source: GitHub Actions. The workflow builds and
   publishes on every push that touches `frontend/`.
4. Check `<api-url>/health` returns `{"status":"ok"}` and the site loads.

## Admin account and demo data

Register an account in the app, then promote it from a machine that has the connection string:

```bash
cd backend
read -rs DATABASE_URL && export DATABASE_URL     # paste the string, nothing is echoed
.venv/bin/python -m app.make_admin you@example.com
unset DATABASE_URL
```

The demo data (`python -m app.seed`, run the same way) creates accounts with the published
password `demo1234`. Only use it on a throwaway demo. It is safe to run twice, but it does not undo
changes visitors have made.

## Updating

Push to `main`. Render redeploys the API and the Pages workflow republishes the front end. CI runs
on the same push. Both providers can redeploy an earlier build from their dashboards. Migrations do
not roll back automatically.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Browser console shows a CORS error | `CORS_ORIGINS` doesn't exactly match the site's origin (scheme and host, no trailing slash). |
| First request after a quiet period is slow | The free API (and database) are waking up. |
| Deploy fails with "SECRET_KEY must be set" | `ENVIRONMENT=production` without a private `SECRET_KEY`. |
| Connection or SSL errors in the API logs | The Neon string is truncated or missing `sslmode=require`. |
| Site requests `/api/...` and gets 404 | `VITE_API_URL` wasn't set when the front end was built. |
| 429 on login | Too many failed attempts; it clears after 15 minutes or when the API restarts. |

## Notes

- `/health` deliberately doesn't query the database, so health checks never wake Neon.
- Login rate limits are held in memory and reset on restart. The per-IP limit relies on the
  forwarded client address, which a caller can spoof; the per-email limit is the backstop.
- The login token is stored in `localStorage`, which is shared by everything under
  `<owner>.github.io`. A custom domain would isolate it.
- Migrations run when the API starts. With more than one instance they should be a separate step.
